Providers are server-side adapters behind the public content APIs. The filesystem provider is the default. External providers can supply the same website-shaped contract from another source such as a database, company CMS, or future Ginko CMS provider.

Register external providers in `content.config.ts`:

```ts [content.config.ts]
import { defineCollection, defineContentConfig } from '@lupinum/ginko-content/config'
import { z } from 'zod'

export const docs = defineCollection({
  type: 'page',
  source: 'docs/**/*.md',
  schema: z.object({
    title: z.string()
  })
})

export default defineContentConfig({
  provider: process.env.CONTENT_PROVIDER === 'custom' ? 'custom' : 'filesystem',
  providers: {
    custom: '@acme/content-provider'
  },
  collections: { docs }
})
```

## Contract

External providers should implement the `ContentProvider` type from `#content/server`:

```ts
import type { ContentProvider } from '#content/server'

export default {
  name: 'custom',
  capabilities: {
    routeBackedCollections: true,
    dataCollections: true,
    localizedRoutes: true,
    translatedSlugs: true,
    navigation: true,
    surroundings: true,
    searchSections: true,
    sitemap: true,
    query: {
      operators: ['$eq', '$ne', '$in'],
      limit: true,
      skip: true,
      count: true
    }
  },
  async page(event, collection, routeOrPath, options) {},
  async query(event, query) {
    return {
      result: [],
      skip: query.skip || 0,
      limit: query.limit || 0,
      total: 0
    }
  },
  async navigation(event, collection, options) {},
  async navigationQuery(event, query) {},
  async surroundings(event, collection, path, options) {},
  async routeMeta(event, collection, routeOrPath, options) {},
  async searchSections(event, collection, options) {},
  async sitemapEntries(event, options) {}
} satisfies ContentProvider
```

The content engine validates loaded external providers and query results. A malformed provider fails with `provider_module_invalid`; a provider module that cannot be loaded fails with `provider_module_missing`; a malformed provider query result fails with `provider_result_invalid`.

`query()` must return canonical query envelopes. List queries return
`{ result: T[], skip, limit, total }`, first queries return
`{ result: T | undefined }`, and count queries return `{ result: number }`.
Raw arrays, raw documents, raw numbers, and `undefined` are rejected.

## Cache-aware results

Providers can attach cache metadata to any method result with `withContentCache()`:

```ts
import { withContentCache, type ContentProvider } from '#content/server'

async function page(event, collection, routeOrPath) {
  const page = await loadPage(collection, routeOrPath)
  if (!page) return null

  return withContentCache(page, {
    tags: [
      `entry:${collection}:${page.ref}`,
      `collection:${collection}`,
      `route:${page.path}`,
      ...page.authorRefs.map(ref => `entry:authors:${ref}`)
    ],
    paths: [page.path],
    maxAge: 300,
    swr: 60,
    lastModified: page.updatedAt
  })
}
```

The wrapper is explicit and does not collide with real content fields named `data` or `cache`. Runtime callers still receive the original `page` shape; Ginko records the hint request-locally and passes the merged hint to the configured cache adapter.

Providers that own backend caches should also implement `invalidate(event, input)`. The built-in revalidation endpoint calls it with normalized paths and tags after token validation.

```ts
async invalidate(event, input) {
  await providerCache.purge(input)
}
```

See [CMS Cache and Invalidation](/docs/cms-cache) for standard tags and publish-webhook behavior.

## Conformance Fixture

Use the package fixture when you are building a new provider and want a known-good contract target before connecting a real backend:

```ts
import {
  createFixtureContentProvider,
  createProviderFixtureEvent,
  createSaasProviderFixture
} from '@lupinum/ginko-content/testing/provider-fixture'

const fixture = createSaasProviderFixture()
const provider = createFixtureContentProvider(fixture)
const event = createProviderFixtureEvent({ fixture, provider })

const page = await provider.page(event, 'docs', '/de/dokumentation/einstieg')
const posts = await provider.query(event, {
  collection: 'posts',
  resolveLocale: { locale: 'de', fallback: false },
  sort: [{ date: -1 }]
})
const rows = posts.result
```

The fixture implements a route-backed, localized provider with page/data collections, navigation, surroundings, search sections, sitemap entries, provider search, and site data. It is intentionally small enough to copy into a provider package test suite and replace one method at a time with backend calls.

## Capabilities

Capabilities are runtime truth, not marketing. Providers must declare every capability field explicitly. If a provider cannot support an operation or query shape correctly, it must set the relevant capability to `false`, leave unsupported query operators out of `query.operators`, and throw a typed provider error when callers request unsupported behavior.

Rules:

- route-backed collections may participate in page, route meta, navigation, surround, search, and sitemap operations
- data-only collections may participate in query/list operations
- data-only route, search, or sitemap access must fail clearly unless a future data-search contract explicitly supports it
- `routeMeta` is a provider operation for page rendering and locale switchers,
  not a standalone HTTP facade endpoint in the first-party CMS provider.
- unsupported query operators must fail with `unsupported_query_operator`
- unsupported sort or projection shapes must fail clearly from the provider; sortable and projectable fields are provider-specific and are not advertised as generic capabilities
- unknown collections must fail with `unknown_collection`
- missing localized routes should return not found behavior, not fallback content pretending to be localized

## Errors

Use `createContentProviderError()` from `#content/server` for stable errors:

```ts
import { createContentProviderError } from '#content/server'

throw createContentProviderError('unsupported_query_operator', 'Operator is not supported.', {
  operator: '$near'
})
```

Stable provider error codes include:

- `unknown_provider`
- `unknown_collection`
- `unsupported_provider_operation`
- `unsupported_query_operator`
- `unsupported_query_shape`
- `data_collection_route_access`
- `data_collection_search_access`
- `data_collection_sitemap_access`
- `missing_locale_route`
- `provider_config_missing`
- `provider_module_missing`
- `provider_module_invalid`
- `provider_result_invalid`
- `unsupported_provider_search_index`
- `unsupported_provider_search`
- `unsupported_provider_site_data`
- `unsupported_provider_prerender`

## Production Expectations

A production provider should be covered by the same conformance tests as the filesystem provider:

- page found and not found
- localized page found and missing localized route
- query filtering, sorting, projection, limit, skip, first, and count
- navigation tree
- surroundings
- search sections
- sitemap entries
- route-backed vs data-only collection rules
- unsupported query operators and unsupported shapes
- provider misconfiguration and remote backend failures
