---
title: Production readiness
description: What Ginko Content supports today, what to verify before release, and which deployment limits are intentional.
---

Ginko Content is designed for production Nuxt sites that want content files,
typed collections, route-backed rendering, i18n, search, sitemap output, and
agent-readable markdown from one content model.

## Supported stack

Use the package with:

- Node.js 20 or later
- Nuxt 4.4.7 or later
- Vue 3.5 or later

The filesystem provider is the default and most exercised provider. Custom
providers should pass the provider conformance tests before they are treated as
production-ready.

## Stable user path

For normal sites, keep the model small:

- define collections in `content.config.ts`
- render route-backed pages with `useContentPage(handle)`
- query lists and detail records through collection handles
- let Ginko own content routes, navigation, search records, and sitemap entries
- let Nuxt I18n own static app page paths
- let `@nuxtjs/sitemap` own final XML output

Advanced surfaces such as provider contracts, cache revalidation, CMS contract
artifacts, and agent-readable markdown are optional. They are not required for a
basic docs, marketing, or blog site.

## Static and SSR behavior

Generated static sites should use explicit generated markdown routes:

- `/raw/**.md`
- `/:route/index.md`
- `/llms.txt`
- `/llms-full.txt`

Same-URL `Accept: text/markdown` negotiation is an SSR or hybrid Nitro
middleware behavior. It is not a pure static hosting guarantee for prerendered
HTML, because a static host can serve `index.html` without running Nitro
middleware. This is a deployment constraint, not a hidden fallback.

Agent `Link` headers follow the same rule: they are reliable when Nitro handles
the request. For pure static hosting, link directly to the generated markdown
files.

## What this package does not own

Ginko Content is the content engine and default filesystem provider. It does not
ship a CMS Studio, admin UI, MCP workflow host, editorial approval system, or
database bridge.

Runtime content should integrate through the provider contract. CMS-neutral
contract and import helpers are available for tooling, but CMS runtime behavior
belongs in a separate package or app layer.

## Release checks

Before publishing a site that depends on advanced behavior, verify the relevant
mode from production output:

- build the Nuxt app
- inspect generated sitemap XML and search payloads
- test locale switching in a production browser session
- fetch explicit markdown routes and LLM files when agent output is enabled
- run provider conformance tests for custom providers
- install the packed package into a fresh Nuxt app before publishing a package

The Ginko repository release gate runs these checks through `pnpm run
release:verify`.
