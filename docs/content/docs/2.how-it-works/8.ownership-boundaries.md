---
title: Ownership Boundaries
description: Ginko coordinates content facts while Nuxt, Nuxt I18n, Nuxt Sitemap, providers, applications, and CMS products retain distinct responsibilities.
---

Ginko stays coherent by assigning each fact to one owner.

## Responsibility map

| Owner | Responsibilities |
| --- | --- |
| Ginko core | Normalized document contract, queries, route projection, rendering integration, variant resolution |
| Filesystem provider | File discovery, parsing input, ordering conventions, draft and partial conventions |
| External provider | Source truth, raw documents, route facts, supported query capabilities, source invalidation |
| Nuxt | Application routes, rendering lifecycle, Nitro deployment, prerender execution |
| Nuxt I18n | Active locale, URL strategy, static application-page localization |
| Nuxt Sitemap | XML, sitemap indexes, robots integration, final serialization |
| Application | Page layouts, 404 UX, component design, access policy, product-specific queries |
| CMS product | Editing, drafts, publishing, roles, assets, workflow, editorial audit |

## Why the split matters

If the application reconstructs content routes, Ginko and the UI can disagree. If Ginko owns XML, sitemap-specific deployment concerns enter the content engine. If a provider reads application locale state directly, background jobs become unpredictable.

The boundary is therefore behavioral, not organizational:

- providers return source facts;
- Ginko applies content and route policy;
- integrations project those facts into their own formats;
- applications decide presentation and product behavior.

## Common ownership mistakes

Avoid these patterns:

- maintaining a second application route table for content pages;
- filtering sitemap locales independently from document variants;
- making a provider inspect preview cookies or deployment environment itself;
- storing canonical identity in frontend state;
- adding CMS workflow fields to the filesystem provider contract;
- teaching removed APIs through compatibility wrappers.

## Extension rule

When adding a capability, put the invariant at the lowest framework-neutral layer that owns the fact. Keep Vue, Nitro, and transport code as adapters over that behavior.
