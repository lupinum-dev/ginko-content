---
title: Query Model
description: Ginko uses collection-first verbs for single documents, lists, pages, navigation, and surroundings across client and server code.
---

Ginko exposes one query vocabulary instead of separate path, collection, and provider APIs.

## Core verbs

| Verb | Result |
| --- | --- |
| `one` | The first matching document or `null` |
| `many` | All matching documents |
| `paginate` | Documents plus paging metadata |
| `resolveOne` | One route-aware document with locale resolution |
| `navigation` | A collection navigation tree |
| `surround` | Previous and next entries around a document |

Client and server code use the same operations. Server calls receive the active H3 event as the first argument so provider and request context remain explicit.

## Collection-first calls

```ts
import { blog } from '~/content.config'

const posts = await many(blog, {
  where: {
    publishedAt: { $exists: true }
  },
  sort: { publishedAt: 'desc' },
  select: ['title', 'description', 'publishedAt']
})
```

The collection handle supplies the document type. Options describe filtering, sorting, projection, paging, and locale behavior without creating a mutable builder chain.

## Route-backed pages

Page components normally use `useContentPage(handle)`. It resolves the current route, suppresses stale data during navigation, and can request surroundings in the same page model.

```ts
const { page, previous, next } = await useContentPage(docs, {
  surround: { select: ['description'] }
})
```

The composable does not throw a default 404. The page owns that user-facing decision.

## Provider capabilities

Every provider advertises supported query operators and pagination modes. Ginko rejects unsupported shapes with provider errors instead of silently changing semantics.

This makes capability metadata executable: if a provider advertises `$contains`, its contract tests must prove `$contains` works.

## Invariant

Filtering, route resolution, navigation, and provider dispatch must not create competing query lanes. New operations should use the existing collection handle and normalized result model.
