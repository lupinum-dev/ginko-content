---
title: Collections
description: A collection owns a group of documents and carries their source, schema, route, localization, and query types.
---

A collection is the boundary around a group of content. Every public Ginko read targets one.

```ts [content.config.ts]
import { defineCollection, defineContentConfig } from '@lupinum/ginko-content/config'
import { z } from 'zod'

export const blog = defineCollection({
  type: 'page',
  source: 'blog/**/*.md',
  route: '/blog',
  schema: z.object({
    title: z.string(),
    description: z.string().optional(),
    date: z.string()
  })
})

export default defineContentConfig({
  collections: { blog }
})
```

## What a collection owns

- **Source:** which files or provider documents belong to the collection.
- **Kind:** `page` for route-backed content or `data` for structured records.
- **Schema:** the authored fields documents must satisfy.
- **Route mount:** where page documents appear publicly.
- **Localization:** whether and how locale variants are grouped.
- **Types:** the result shape returned through the collection handle.

## Why handles matter

`defineCollection()` returns a typed handle. Export it from `content.config.ts` and pass it to public helpers:

```ts
const post = await one(blog, {
  where: { date: { $exists: true } },
  sort: { date: 'desc' }
})
```

Application code does not pass a free-form collection name when a handle is available. The handle preserves schema inference and makes the collection dependency explicit.

## Page and data collections

Use `type: 'page'` when each entry has a public content route. Page collections participate in route resolution, navigation, sitemap, and prerender according to their options.

Use `type: 'data'` for authors, products, configuration, or other structured records that are queried but do not automatically represent public pages. Data collections are excluded from sitemap output by default.

## Collection names

The key in `defineContentConfig({ collections })` is the canonical collection name. Exported handles are normally declared with the same identifier to keep code and diagnostics aligned.

## Invariant

Do not create a global path lookup beside collection queries. That would detach documents from their schema and policy, producing a second content model.
