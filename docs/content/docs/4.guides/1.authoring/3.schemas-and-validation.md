---
title: Schemas and Validation
description: Define Zod schemas at the collection boundary so invalid authored data fails before pages and queries consume it.
---

Put content invariants in the collection schema. Page components should receive valid content, not repeat frontmatter checks.

## Define the schema

```ts [content.config.ts]
import { defineCollection, defineContentConfig } from '@lupinum/ginko-content/config'
import { z } from 'zod'

export const posts = defineCollection({
  type: 'page',
  source: 'blog/**/*.md',
  route: '/blog',
  schema: z.object({
    title: z.string().min(1),
    description: z.string().min(1),
    publishedAt: z.iso.datetime(),
    tags: z.array(z.string()).default([]),
    featured: z.boolean().default(false)
  })
})

export default defineContentConfig({ collections: { posts } })
```

Schema inference flows through the exported `posts` handle into `one`, `many`, `useContentPage`, and server operations.

## Keep defaults at ingestion

Use schema defaults for authored fields with one domain default. Do not repeat `post.tags || []` across page components.

Do not use a default when omission and an explicit value have different meaning.

## Configure validation behavior

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  content: {
    validation: 'error'
  }
})
```

Strict validation is appropriate for production documentation and application content because a bad document should fail the build that introduced it. Use the supported module option values from [Module options](/docs/reference/module-options); do not invent per-page validation modes.

## Validate references separately

A field can be a valid string and still point to missing content. Use `reference()` for content relations so Ginko can validate the target against collection identity.

## Verify

Add one intentionally invalid fixture locally and confirm the build reports the collection, file, field, and validation cause. Remove the invalid fixture before committing.

## Failure modes

- The schema duplicates built-in route fields.
- Components silently coerce invalid data.
- A schema default hides a meaningful omitted state.
- Studio-specific schema extensions are copied into plain Zod.
- Validation differs between development and CI without an explicit reason.
