---
title: When to Use a Provider
description: Replace the filesystem provider only when a real content source or runtime publishing requirement justifies the additional contract.
---

Keep the filesystem provider until the project has a concrete source requirement it cannot satisfy.

## Stay with the filesystem provider when

- Markdown and Git are the authoring workflow;
- content changes can deploy with the application;
- the corpus fits the documented small-to-medium target;
- built-in search modes are sufficient;
- branches provide an acceptable preview workflow.

The provider abstraction is not a reason to create an application service around filesystem reads.

## Introduce a provider when

- a CMS or database is the canonical content source;
- publishing must happen independently from application deployment;
- provider-owned search is required;
- runtime access control changes which documents are available;
- the content corpus or query load has outgrown local filesystem artifacts;
- several applications need one published content source.

## What a provider changes

The provider owns source access and advertises executable capabilities. It returns raw documents and route facts. Ginko still owns normalized document envelopes, public route projection, application APIs, and content integration behavior.

Application pages should continue to call `useContentPage`, `one`, `many`, `navigation`, and other public operations with the same collection handles.

## What a provider does not add automatically

A provider contract does not create:

- an editorial UI;
- draft and publish workflows;
- authentication or permissions;
- media management;
- search indexing;
- cache invalidation delivery.

The source product or integration must implement the capabilities it needs.

## Decision checklist

Before building a provider, record:

1. The canonical external source.
2. Required query operators and pagination mode.
3. Route and locale facts available from that source.
4. Search ownership.
5. Preview and visibility behavior.
6. Cache and invalidation requirements.
7. Contract tests that prove the advertised behavior.

If those requirements are unknown, a generic provider layer is premature.

## Verify the decision

The provider is justified only when every item below is true:

- the filesystem provider cannot meet a named requirement;
- the external source is already chosen;
- its supported queries, routes, locales, and visibility rules are known;
- search and cache ownership have named owners;
- contract tests can prove every advertised capability.

If any item is unresolved, keep the filesystem provider and revisit the decision when the requirement is concrete.
