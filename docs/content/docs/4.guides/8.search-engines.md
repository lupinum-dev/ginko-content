---
title: Choose and configure search
description: Pick MiniSearch, Pagefind, provider search, or an external service, then configure the one you chose.
---

Match your requirement to a backend, then set it up:

| Requirement | Choose |
| --- | --- |
| Small-to-medium content site, static or SSR output | MiniSearch |
| Larger generated site that benefits from shard loading | Pagefind |
| A content provider already indexes your content | Provider search |
| Hosted ranking, analytics, typo tuning, or a very large corpus | External service |

Search is off by default. Set `content.search: {}` to turn on MiniSearch, or name another engine.

## MiniSearch

The default. Ginko builds one JSON index and you query it with `useContentSearch`. Configure it in `nuxt.config.ts`:

```ts [nuxt.config.ts]
content: {
  search: {
    engine: 'minisearch',
    ignoredTags: ['script', 'style', 'pre'],
    filterQuery: { draft: false, partial: false },
    minisearch: {
      fields: ['title', 'content', 'headings', 'tags'],
      boost: { title: 4, headings: 2, tags: 3, content: 1 },
      fuzzy: 0.2
    }
  }
}
```

`fields` are what MiniSearch indexes, `boost` weights each field's relevance, and `fuzzy` sets how much typo tolerance you allow. When you omit `collections`, Ginko indexes public route-backed collections and leaves data collections out.

The trade-off is index size: the JSON grows with your content and ships to every browser. Measure the compressed index and the time to first result. When that payload becomes a cost your readers actually feel, move to Pagefind.

## Pagefind

Pagefind indexes your generated HTML into shards the browser loads on demand, so nothing downloads one full corpus up front. Install it first, it is an optional peer dependency:

```bash
pnpm add pagefind
```

```ts [nuxt.config.ts]
content: {
  search: {
    engine: 'pagefind'
  }
}
```

Pagefind needs generated output, so build with `pnpm generate` and deploy the whole directory, including the `pagefind/` assets. Your component code stays the same: Ginko normalizes Pagefind hits into the result shape MiniSearch and provider search already use, so `useContentSearch` does not change.

> **Pagefind only sees the last generated site.** Content added at runtime, after a build, will not appear in search until you regenerate and redeploy. If your content changes independently of the build, stay on MiniSearch or provider search.

## Provider search

When a content provider already indexes your content, set `engine: 'provider'` and the provider returns the hits while Ginko applies your public path rules. See [Provider search and caching](/docs/guides/provider-search-and-caching).

## External services

Algolia, Meilisearch, Typesense, and friends are a good fit when search is a product feature in its own right, with hosted ranking, analytics, synonyms, and facets. Their UI sits outside `useContentSearch`, so keep the result URLs pointed at your real content routes.

## One rule for production

Keep a single search backend. Running two side by side gives you two indexes to keep in sync and two ways for search to break. And test search in a production preview, not just in dev, so you catch a missing index or unshipped assets before your readers do.
