---
title: How Ginko thinks
description: The mental model behind Ginko - collections, one document shape, typed queries, and everything else generated from your files.
---

Ginko has one content flow: your files become normalized documents, and every feature reads from those documents.

```txt
content files or provider
          │
          ▼
      collection
          │
   parse → validate → normalize
          │
          ├── resolve pages and translations
          ├── run typed queries
          ├── build navigation and surroundings
          ├── produce search records
          └── produce sitemap and prerender routes
```

## Collections group your files

A collection owns a group of files, their schema, and the URL where they mount.

```ts [content.config.ts]
import { defineCollection, defineContentConfig } from '@lupinum/ginko-content/config'
import { z } from 'zod'

export const blog = defineCollection({
  type: 'page',
  source: 'blog/**/*.md',
  route: '/blog',
  schema: z.object({
    title: z.string(),
    description: z.string().optional(),
    date: z.string()
  })
})

export default defineContentConfig({
  collections: { blog }
})
```

`defineCollection` returns a typed handle - here it is `blog`. Import it, pass it to any query, and results are typed against your schema. That handle is your one reference to a collection in code, and it is what keeps every query typed.

## One document shape

Every query returns the same document shape, whatever the source - a Markdown file, a structured data record, or an external provider. Alongside your schema fields, each page carries a `route` and a `resolution`, so any result can be linked and its language known without a second lookup.

## Which URL, which language

Three questions, three fields on every page:

- What URL do I link to? `route.resolvedPath`. Never the file path.
- Where is this page in other languages? `route.alternates`. A language switcher is a loop over it.
- Did the reader get a fallback? `resolution.usedFallback`. A fallback is content shown from another language when the requested one has no translation.

`canonicalKey` is the opaque shared ID that ties a page to its translations - good as a list key, never a URL.

## One query vocabulary

For route-backed pages, `useContentPage(handle)` resolves the current route into a page model:

```ts [pages/blog/[...slug].vue]
const { page, previous, next } = await useContentPage(blog, {
  surround: { select: ['description'] }
})
```

For everything else, `one`, `many`, `paginate`, `navigation`, and `surround` are pure functions you wrap in `useAsyncData`:

```ts
const posts = await many(blog, {
  where: { publishedAt: { $exists: true } },
  sort: { publishedAt: 'desc' }
})
```

The same verbs run on the server - pass the request event as the first argument, so provider and locale context stay explicit.

## Everything else is generated

Navigation, search records, sitemap entries, and prerender routes all come from the same documents. Discard any of them and Ginko rebuilds it from your files. Your files stay the only thing you maintain.
