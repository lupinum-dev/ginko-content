title: Ship to Production
description: Build the site, verify route and search artifacts, and choose a supported SSR or static deployment shape.
---

Ginko supports Nuxt's SSR, static, serverless, and edge deployment targets. The content contract stays the same; generated artifacts and runtime capabilities differ by target.

## Build the application

```bash
pnpm build
```

Preview the exact build:

```bash
pnpm preview
```

Check at least:

- the home page and one nested content page;
- the application's 404 response;
- navigation links;
- one search result and heading anchor;
- page metadata;
- direct loading of a nested route.

## Static generation

For a generated site, run the application's normal Nuxt generation command:

```bash
pnpm generate
```

Ginko contributes eligible page-collection routes to prerender discovery. Drafts, partials, and excluded sitemap content do not become public routes.

Serve the generated directory through a local static server before deployment. Opening HTML files directly does not reproduce asset paths, routing, or content negotiation.

## SSR and serverless

SSR deployments use the active provider during requests. The filesystem provider reads prepared content artifacts; an external provider may make runtime network requests and return cache hints.

Keep provider credentials server-only. Do not expose provider clients through page components.

## Production checklist

- Run type checking after content schemas change.
- Confirm all content links resolve.
- Confirm drafts and partials are hidden outside development.
- Test locale fallback and alternates when i18n is enabled.
- Verify sitemap XML through `@nuxtjs/sitemap` when configured.
- Verify MiniSearch or Pagefind assets in the deployed output.
- Pin versions according to the application's release policy.

## Ginko repository checks

Contributors to Ginko itself use:

```bash
pnpm docs:build
pnpm docs:smoke
pnpm docs-drift
pnpm verify
```

Application consumers should use their own build, typecheck, test, and deployment gates rather than copying the repository's release pipeline.
