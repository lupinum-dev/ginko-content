The module infers locale from the URL or filename, resolves fallback chains when a translation is missing, and exposes locale metadata on every document.

## Declaring locales

Declare locale behavior in `nuxt.config.ts` with `content.i18n`.

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  content: {
    i18n: {
      defaultLocale: 'en',
      locales: ['en', 'fr', 'de'],
      fallback: {
        fr: ['en'],
        de: ['en']
      },
      translatedSlugs: true
    }
  }
})
```

| Field | Purpose |
|---|---|
| `defaultLocale` | Locale served when the URL has no explicit locale |
| `locales` | Every locale the site serves |
| `fallback` | Per-locale fallback chains |
| `translatedSlugs` | Use numeric prefixes as the cross-locale identity source |

`translatedSlugs` is opt-in. Shared slugs across locales work without it.

## Common layouts

### Shared slug

One URL slug, one file per locale, grouped by top-level locale folder:

```txt
content/
  en/
    docs/
      getting-started.md
  fr/
    docs/
      getting-started.md
```

This yields `/docs/getting-started` for English and `/fr/docs/getting-started` for French.

### Translated slugs

Use numeric prefixes so translated folder names still map back to one canonical document identity:

```txt
content/
  en/
    1.guide/
      1.getting-started.md
  de/
    1.leitfaden/
      1.erste-schritte.md
```

With `translatedSlugs: true`, those files share one `_canonicalKey`.

## Querying a locale

`locale` restricts a query to one locale:

```ts
const frenchArticles = await many(articles, {
  locale: 'fr'
})
```

Without `locale`, results can span every locale in the collection.

## Locale in the URL

With the default router integration, the first URL segment is treated as a locale when it matches one of `locales`:

- `/docs/getting-started` → locale `en` (default)
- `/fr/docs/getting-started` → locale `fr`

Localized documents carry public resolution metadata on `resolved`. Use that object in UI code instead of private storage fields:

```ts
page.value?.resolved.locale
page.value?.resolved.requestedLocale
page.value?.resolved.fallback
page.value?.resolved.fallbackLocale
```

## Canonical identity

Across locales, the same logical document shares a `_canonicalKey`. Use it when you need to relate translated variants in a query:

```ts
import { docs } from '~/content.config'

const { page } = await useContentPage(docs, {
  fallback: true
})

const alternates = await many(docs, {
  where: { _canonicalKey: page.value?._canonicalKey || '' }
})
```

This is useful for content relationships and audits. It is not the preferred locale-switch contract for routed pages.

## Nuxt I18n route sync

When a page is rendered through a localized dynamic route such as `/docs/[...slug]` or `/blog/[slug]`, use `useContentPage()`.

```ts
const { page } = await useContentPage(docs, {
  fallback: true
})
```

This keeps page-level locale switchers and Nuxt I18n route params aligned with the localized paths that Ginko resolves from the content graph.

Treat `page.localePaths` as the public content locale-switch contract. Route-backed `useContentPage()` results publish those paths so switchers and localized head output stay correct. For standalone switchers, resolve the active document with `useContentOne()` or `useContentVariants()` and read `localePaths` directly; keep route-only Nuxt I18n switching as the fallback when no content document is resolved.

```ts
const route = useRoute()
const { data: page } = await useContentOne(docs, {
  by: { route: () => route.path },
  fallback: true
})

const items = computed(() =>
  locales.value.map(item => ({
    label: item.name || item.code,
    to: item.code === locale.value ? undefined : page.value?.localePaths[item.code]?.path
  }))
)
```
