---
title: From Nuxt Content v3
description: Move a Nuxt Content v3 site to the Ginko collection-first runtime.
---

Nuxt Content v3 and Ginko both use collections, `content.config.ts`, `many()`, and `<ContentRenderer>`. Ginko keeps the object-shaped `defineCollection({ type, source, schema })` declaration and uses the `collections` map key as the collection identity.

## Who needs this guide

Use this guide if your app already runs on `@nuxt/content` v3 and has code shaped like this:

- old Nuxt Content v3 `defineCollection({ type: 'page', source: ... })`
- `queryCollection('docs').path(route.path).first()` (old Nuxt Content v3 API)
- `queryCollectionItemSurroundings('docs', route.path)`
- `useContentSearchData('docs')`
- `ContentRenderer :value="page"`
- Nuxt UI `UContentSearch` fed by `useContentSearchData()`

If your app still uses Nuxt Content v2 APIs such as `queryContent()` or `ContentDoc`, start with [From Nuxt Content v2](/docs/migration/from-nuxt-content-v2).

## Replace the package

Replace `@nuxt/content` with `@lupinum/ginko-content`:

::code-group
```bash [pnpm]
pnpm remove @nuxt/content
pnpm add @lupinum/ginko-content
```

```bash [npm]
npm uninstall @nuxt/content
npm install @lupinum/ginko-content
```

```bash [yarn]
yarn remove @nuxt/content
yarn add @lupinum/ginko-content
```
::

Then update `nuxt.config.ts`:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['@lupinum/ginko-content']
})
```

Do not keep `@nuxt/content` in `modules`. Ginko replaces the Nuxt Content module; running both modules in one app creates duplicate auto-imports, components, runtime config, and content routes.

Remove v3-only `content.database` and `content.build` database assumptions as you migrate. Ginko does not use the v3 client SQLite/WASM query runtime. Ginko has its own `content.preview` option (a server-side token that gates draft/partial visibility for the filesystem provider); keep it if you already configured it, but note it always applies in development and, in production, only reveals drafts/partials already present in the deployed content directory — it does not fetch not-yet-published content the way a CMS provider's preview mode can.

If `@nuxt/content`, `better-sqlite3`, or `@standard-schema/spec` still appears in the lockfile after removal, check why before forcing it out:

```bash
pnpm why @nuxt/content better-sqlite3 @standard-schema/spec
```

Those packages may still be transitive dependencies of Nuxt UI, Nitro storage, or SEO tooling. The migration goal is to remove Nuxt Content as an app dependency and Nuxt module, not to rewrite unrelated upstream dependency graphs.

## Move collection declarations

Nuxt Content v3 declares a collection inside the `collections` object with an object-only `defineCollection()` call:

```ts [content.config.ts]
import { defineCollection, defineContentConfig } from '@nuxt/content'
import { z } from 'zod'

// Old Nuxt Content v3 API
export default defineContentConfig({
  collections: {
    docs: defineCollection({
      type: 'page',
      source: {
        include: 'docs/**/*.md',
        exclude: ['docs/private/**']
      },
      schema: z.object({
        title: z.string(),
        description: z.string().optional()
      })
    })
  }
})
```

In Ginko, you may keep the collection inline or assign it to a local/exported handle. The `collections` map key is still the query name:

```ts [content.config.ts]
import { defineCollection, defineContentConfig } from '@lupinum/ginko-content/config'
import { z } from 'zod'

export const docs = defineCollection({
  type: 'page',
  source: {
    include: 'docs/**/*.md',
    exclude: ['docs/private/**']
  },
  schema: z.object({
    title: z.string(),
    description: z.string().optional()
  })
})

export const versions = defineCollection({
  type: 'page',
  source: 'changelog/**/*.md'
})

export default defineContentConfig({
  collections: { docs, versions }
})
```

Key differences:

| Nuxt Content v3 | Ginko |
|---|---|
| `defineCollection({ type, source, schema })` | `defineCollection({ type, source, schema })` |
| collection key names the query collection | same: the `collections` map key is canonical |
| `type: 'page'` | route-backed content collection |
| `type: 'data'` | data collection; defaults to `sitemap: false` |
| `source.include` / `source.exclude` | supported |
| `import { defineCollection } from '@nuxt/content'` | `import { defineCollection } from '@lupinum/ginko-content/config'` |
| `z` can be re-exported from `@nuxt/content` | import `z` from `zod` |
| Nuxt Studio `.editor(...)` helpers on Zod fields | remove them, or move editor-only metadata outside the runtime schema |

When a v3 collection used `type: 'data'`, keep it as a data collection and query it by name. Ginko excludes data collections from sitemap and prerender route discovery by default:

```ts
export const authors = defineCollection({
  type: 'data',
  source: 'authors/**/*.yml',
  schema: z.object({
    name: z.string(),
    avatar: z.string().url().optional()
  })
})
```

Nuxt Content Studio examples sometimes attach `.editor(...)` to Zod fields. Plain `zod` does not provide that method, so remove those calls before type-checking:

```ts
// Before
image: z.string().editor({ input: 'media' })

// After
image: z.string()
```

## Move route pages to `useContentPage`

In v3, catch-all pages commonly own route resolution and 404 handling:

```vue [pages/docs/[...slug].vue]
<script setup lang="ts">
const route = useRoute()

const { data: page } = await useAsyncData(route.path, () => {
  // Old Nuxt Content v3 API
  return queryCollection('docs')
    .path(route.path)
    .first()
})

if (!page.value) {
  throw createError({ statusCode: 404, statusMessage: 'Page not found', fatal: true })
}
</script>

<template>
  <ContentRenderer v-if="page" :value="page" />
</template>
```

In Ginko, route-backed pages should use `useContentPage()`:

```vue [pages/docs/[...slug].vue]
<script setup lang="ts">
import { createError } from '#imports'
import { docs } from '~/content.config'

const { page, previous, next } = await useContentPage(docs, {
  surround: { select: ['description'] }
})

if (import.meta.server && !page.value) {
  throw createError({ statusCode: 404, statusMessage: 'Page not found' })
}
</script>

<template>
  <ContentRenderer v-if="page" :value="page" />

  <nav v-if="previous || next">
    <NuxtLink v-if="previous" :to="previous.path">
      {{ previous.title }}
    </NuxtLink>

    <NuxtLink v-if="next" :to="next.path">
      {{ next.title }}
    </NuxtLink>
  </nav>
</template>
```

`useContentPage()` resolves the current route, publishes route/resolution metadata, suppresses stale route data during navigation, and can load previous/next data when `surround` is enabled. It does not raise a default 404 — check `page.value` and `throw createError(...)` yourself, as shown above.

Use the same pattern for single-segment route pages such as `/blog/[slug].vue` and `/changelog/[slug].vue`. If a content collection contributes URLs to navigation or sitemap, the Nuxt app still needs a matching page component for those URLs:

```vue [pages/changelog/[slug].vue]
<script setup lang="ts">
import { versions } from '~/content.config'

const { page: version, previous, next } = await useContentPage(versions, {
  surround: { select: ['description'] }
})
</script>

<template>
  <ContentRenderer v-if="version" :value="version" />
</template>
```

Do not render `version.body` directly. Ginko's `<ContentRenderer>` expects the full content document so it can read body, metadata, table of contents, and component context from one value.

## Move list pages to `many()`

List pages should pair `many()` with `useAsyncData`. It applies the active locale and returns a `route` (with `resolvedPath`) on each item for links.

Nuxt Content v3 examples often select `path`, `id`, `stem`, and `extension`:

```ts
// Old Nuxt Content v3 API
const posts = await queryCollection('blog')
  .select('title', 'description', 'path', 'id', 'date')
  .order('date', 'DESC')
  .all()
```

Raw Ginko query results carry a `route` object instead of a bare `path`. List UI
should link with `item.route.resolvedPath` so locale and route mounts are
already applied:

```ts
import { useAsyncData } from '#imports'
import { many } from '@lupinum/ginko-content/client'

const { locale } = useI18n()
const { data: posts } = await useAsyncData(
  () => `blog-posts:${locale.value}`,
  () => many(blog, { locale: locale.value, sort: { date: 'desc' } }),
  { watch: [locale] }
)
```

Use `route.resolvedPath` from `many()` for links:

```vue
<NuxtLink :to="post.route.resolvedPath">
  {{ post.title }}
</NuxtLink>
```

Route-backed `useContentPage()` payloads also expose route metadata as `route`
(`requestedPath`, `resolvedPath`, `alternates`) and `resolution`
(`requested.locale`, `resolved.locale`, `usedFallback`), plus `stem` and
`extension` directly on the document.

## Audit v3 page fields

Nuxt Content v3 page collections include fields such as `seo`, `path`, `id`,
`stem`, and `extension`. Ginko keeps `title`, `description`, `body`, table of
contents data, and system metadata, but the system metadata was renamed away
from Nuxt Content's underscore fields.

Common replacements:

| v3 field | Ginko field |
|---|---|
| `page.path` from raw `many()` | `page.route.resolvedPath`; use `page.route.requestedPath` only when you need the exact selector the query used |
| `page.id` | `page.id` |
| `page.extension` | `page.extension` |
| `page.stem` in route pages | `page.stem` |
| `page.seo?.title` | `page.title`, or keep a custom `seo` field in your schema |
| `page.seo?.description` | `page.description`, or keep a custom `seo` field in your schema |

If your v3 template reads `page.seo`, either move those values to `title` and `description`, or declare `seo` in the collection schema and keep using it as custom frontmatter.

## Replace v3 surround queries

Nuxt Content v3 uses `queryCollectionItemSurroundings()`:

```ts
const { data: surround } = await useAsyncData(`${route.path}-surround`, () => {
  return queryCollectionItemSurroundings('docs', route.path, {
    fields: ['description']
  })
})
```

Ginko loads previous/next entries through `useContentPage()` for page components:

```ts
import { docs } from '~/content.config'

const { page, previous, next } = await useContentPage(docs, {
  surround: { select: ['description'] }
})
```

Do not carry `queryCollectionItemSurroundings()` forward. It is not part of the Ginko public API.

## Update navigation

Nuxt Content v3 exposes `useContentTree()`. In Ginko, pair the `navigation()` verb with `useAsyncData` when you need the module-owned navigation tree or links derived from it:

```ts
import { useAsyncData } from '#imports'
import { navigation } from '@lupinum/ginko-content/client'
import { docs } from '~/content.config'

const { data: docsNavigation } = await useAsyncData('docs-navigation', () => navigation(docs))
```

The migration work is usually type and field cleanup:

```ts
import type { ContentNavigationItem } from '@lupinum/ginko-content'

const navigation = inject<Ref<ContentNavigationItem[]>>('navigation')
```

Folder metadata stays `.navigation.yml`. If your v3 app already migrated from the old directory metadata filename, you do not need to rename those files again.

## Update search

Nuxt Content v3 templates commonly fetch Nuxt UI search data directly:

```ts
const { data: navigation } = await useAsyncData('navigation', () => useContentNavigation(docs))
const { data: files } = useLazyAsyncData('search', () => useContentSearchData(docs), {
  server: false
})
```

In Ginko, use `useContentSearch({ collection })` for Nuxt UI `UContentSearch`:

```vue [app.vue]
<script setup lang="ts">
import { useContentSearch } from '@lupinum/ginko-content/client'
import { docs } from '~/content.config'

const {
  query,
  files,
  searchNavigation
} = await useContentSearch({ collection: docs })

provide('navigation', searchNavigation)
</script>

<template>
  <UApp>
    <ClientOnly>
      <UContentSearch
        v-model:search-term="query"
        :files="files"
        :navigation="searchNavigation"
      />
    </ClientOnly>
  </UApp>
</template>
```

Keep the `useContentSearch({ collection })` call outside `ClientOnly` so generated pages can serialize the search payload.

`searchNavigation` from `useContentSearch()` is shaped for `UContentSearch` search UI, not for general layout navigation. If the app also injects navigation into docs layouts, load that separately with `navigation()` and `useAsyncData`:

```ts
import { useAsyncData } from '#imports'
import { navigation, useContentSearch } from '@lupinum/ginko-content/client'

const { data: docsLayoutNavigation } = await useAsyncData('docs-navigation', () => navigation(docs))

const {
  query,
  files,
  searchNavigation
} = await useContentSearch({ collection: docs })
```

## Move markdown runtime options

Nuxt Content v3 uses `content.renderer` and `content.build.markdown` options. Ginko uses `content.markdown`:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  content: {
    markdown: {
      plugins: [
        'toc',
        ['highlight', { theme: 'github-dark' }]
      ],
      tags: {
        code: 'ProseCodeInline',
        pre: 'ProsePre'
      },
      anchorLinks: {
        depth: 4,
        exclude: [1]
      }
    }
  }
})
```

Ginko uses Comark plugins. Do not copy v3 `remarkPlugins` or `rehypePlugins` directly unless you have adapted them to the Ginko markdown plugin boundary.

## Wire sitemap as a release gate

Install and enable Nuxt Sitemap when public content routes should appear in the generated sitemap output:

```bash
pnpm add @nuxtjs/sitemap
```

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['@lupinum/ginko-content', '@nuxtjs/sitemap'],
  site: {
    url: process.env.NUXT_PUBLIC_SITE_URL || 'https://docs.ginko-content.dev'
  },
  content: {
    sitemap: {
      assert: {
        enabled: true,
        mode: 'both',
        minUrlsPerSitemap: 1,
        requiredCollections: ['docs', 'posts']
      }
    }
  }
})
```

Replace `site.url` with the production domain before release. Use `requiredCollections` to catch accidental collection drops, and raise `minUrlsPerSitemap` once you know the expected route count for the site.

After the build, verify the generated public files and sitemap entries from the built output:

```bash
node - <<'NODE'
const { existsSync, readFileSync } = require('node:fs')

const expected = [
  '/',
  '/docs/getting-started',
  '/blog',
  '/blog/hello-world'
]

const sitemapFiles = [
  '.output/public/sitemap.xml',
  '.output/public/sitemap_index.xml',
  ...(existsSync('.output/public/__sitemap__')
    ? require('node:fs').readdirSync('.output/public/__sitemap__')
        .filter(file => file.endsWith('.xml'))
        .map(file => `.output/public/__sitemap__/${file}`)
    : [])
].filter(existsSync)

const urls = sitemapFiles.flatMap(file => [...readFileSync(file, 'utf8').matchAll(/<loc>(.*?)<\/loc>/g)])
  .map(match => new URL(match[1]).pathname)

const outputFileFor = route => route === '/' ? '.output/public/index.html' : `.output/public${route}/index.html`

console.log({
  sitemapUrls: urls.length,
  missingFromOutput: expected.filter(route => !existsSync(outputFileFor(route))),
  missingFromSitemap: expected.filter(route => !urls.includes(route))
})
NODE
```

## Update imports

Use these replacements as a first pass:

| Nuxt Content v3 import | Ginko import |
|---|---|
| `@nuxt/content` config helpers | `@lupinum/ginko-content/config` |
| `@nuxt/content/server` | `@lupinum/ginko-content/server` |
| `@nuxt/content/nitro` | `@lupinum/ginko-content/server` |
| `@nuxt/content` app types | `@lupinum/ginko-content` |
| app composables auto-imported from v3 | only `useContentPage` and the collision-safe `useGinkoContentSearch` alias are auto-imported; import `useContentSearch` and every query helper (`one`, `many`, `paginate`, `resolveOne`, `surround`, `backlinks`, `navigation`, `getCollectionPath`, `querySiteData`) explicitly from `@lupinum/ginko-content/client` and pair query helpers with `useAsyncData` |

Then search the app for v3-only APIs and deleted Ginko composables:

```bash
rg "@nuxt/content|queryCollectionItemSurroundings|useContentOne|useContentMany|useContentHead|useContentTree|useContentNavigation|useContentNeighbors|useContentSwitchLocalePath|useContentSearchData|useContentSearchResults|useContentVariants|content\\.database|content\\.build|better-sqlite3|standard-schema"
```

Run this against source and config first. Lockfile matches can be transitive dependencies; verify them with `pnpm why` instead of deleting packages blindly.

## Verify the migration

Use the app's real release commands, not only a dev server:

```bash
pnpm lint
pnpm typecheck
pnpm build
```

Check the build log for these signals:

- Ginko sitemap assertion passed, if assertions are enabled
- Nitro prerendered the expected public route count
- sitemap output was prerendered. Single-sitemap apps usually emit
  `.output/public/sitemap.xml`; Nuxt Sitemap i18n multi-sitemap output emits
  `.output/public/sitemap_index.xml` plus `.output/public/__sitemap__/*.xml`.
  Submit the sitemap URL generated by the configured mode; do not copy or force
  sitemap files to hide the actual deployment contract.
- no content routes failed with 404 during prerender

Non-blocking warnings from Vite sourcemaps, chunk size, or deployment-specific image binaries still deserve review, but they are not the same as a failed migration.

## Migration checklist

- Replace the package and Nuxt module.
- Update `defineCollection()` imports to `@lupinum/ginko-content/config`.
- Keep `type: 'page'` and `type: 'data'` in collection declarations.
- Remove Nuxt Studio-only Zod `.editor(...)` calls.
- Keep `source.include` / `source.exclude` objects when you already use them.
- Move catch-all route loading to `useContentPage()`.
- Add page components for every content collection route pattern that should render publicly.
- Replace `queryCollectionItemSurroundings()` in page components with `useContentPage(..., { surround })`.
- Audit raw query fields: old `_path` filters use `path`, old `_id` filters use `id`, and route metadata now lives under `route`/`resolution` instead of `file.*`.
- Replace Nuxt UI search boilerplate with `useContentSearch({ collection })`.
- Keep app navigation from `navigation()` + `useAsyncData` separate from search navigation returned by `useContentSearch()`.
- Move markdown runtime config to `content.markdown`.
- Enable `@nuxtjs/sitemap` and `content.sitemap.assert` when the site publishes content routes.
- Run the app's production build and check route pages, navigation, search, prerender output, and sitemap output.
