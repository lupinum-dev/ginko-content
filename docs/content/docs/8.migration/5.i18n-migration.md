---
title: I18n migration recipe
description: Convert a Nuxt Content v3 app with localized routes, content, search, and sitemap output to Ginko.
---

Use this recipe when the app uses `@nuxtjs/i18n` and serves translated content routes. It assumes a top-level locale folder shape such as `content/en/...` and `content/de/...`.

## Target state

After migration, the app should follow these rules:

- `@nuxtjs/i18n` is a direct dependency and module.
- `@lupinum/ginko-content` replaces `@nuxt/content`.
- `content.i18n` in `nuxt.config.ts` declares the runtime locale contract.
- every localized collection has `i18n: true`.
- content files live under `content/<locale>/...`.
- route pages use `useContentPage()`.
- list pages pair `many()` with `useAsyncData` and link with `item.route.resolvedPath`.
- search uses `useContentSearch({ collection }).searchNavigation`.
- generated sitemap output has one child sitemap per locale.
- generated search output contains records for every locale.

## Dependencies

Install the content, locale, and sitemap modules explicitly:

```bash
pnpm remove @nuxt/content
pnpm add @lupinum/ginko-content @nuxtjs/i18n @nuxtjs/sitemap zod
```

If `@nuxt/content`, `better-sqlite3`, or `@standard-schema/spec` still appears in the lockfile, check whether it is direct:

```bash
pnpm why @nuxt/content better-sqlite3 @standard-schema/spec
```

Lockfile-only transitive entries are not migration failures.

## Nuxt config

Keep Nuxt I18n responsible for route prefixes. Keep Ginko responsible for content locale resolution:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  modules: [
    '@nuxtjs/i18n',
    '@lupinum/ginko-content',
    '@nuxtjs/sitemap'
  ],
  site: {
    url: process.env.NUXT_PUBLIC_SITE_URL || 'https://docs.ginko-content.dev'
  },
  i18n: {
    defaultLocale: 'en',
    strategy: 'prefix_except_default',
    locales: [
      {
        code: 'en',
        language: 'en-US',
        name: 'English'
      },
      {
        code: 'de',
        language: 'de-DE',
        name: 'Deutsch'
      }
    ]
  },
  content: {
    i18n: {
      defaultLocale: 'en',
      locales: ['en', 'de'],
      fallback: {
        de: ['en']
      }
    },
    sitemap: {
      assert: {
        enabled: true,
        mode: 'both',
        minUrlsPerSitemap: 1,
        requiredCollections: ['docs', 'posts', 'versions']
      }
    }
  }
})
```

`i18n.locales[].code` and `content.i18n.locales` must use the same locale codes. The language tags such as `en-US` are for Nuxt I18n and sitemap output.

## Content config

Localized collections opt into the runtime locale config with `i18n: true`:

```ts [content.config.ts]
import { defineCollection, defineContentConfig } from '@lupinum/ginko-content/config'
import { z } from 'zod'

export const docs = defineCollection({
  type: 'page',
  source: 'docs/**/*.md',
  i18n: true,
  route: {
    en: '/docs',
    de: '/dokumentation'
  },
  schema: z.object({
    title: z.string(),
    description: z.string().optional()
  })
})

export const posts = defineCollection({
  type: 'page',
  source: 'posts/**/*.md',
  i18n: true,
  schema: z.object({
    title: z.string(),
    description: z.string().optional(),
    date: z.string()
  })
})

export const versions = defineCollection({
  type: 'page',
  source: 'versions/**/*.md',
  i18n: true,
  schema: z.object({
    title: z.string(),
    description: z.string().optional(),
    date: z.string()
  })
})

export default defineContentConfig({
  collections: { docs, posts, versions }
})
```

The `collections` map key is the collection identity in this migration. Keep
localized route mounts visible in the collection config.

Do not put locale prefixes in the collection source. The source is collection-relative under each locale root.

## Content tree

Use the same collection tree beneath each locale:

```txt
content/
  en/
    docs/
      getting-started.md
    posts/
      launch.md
    versions/
      2.0.md
  de/
    docs/
      getting-started.md
    posts/
      launch.md
    versions/
      2.0.md
```

English `/docs/getting-started` and German `/de/docs/getting-started` are one logical document in two locales.

## App search and navigation

Layout navigation and search navigation are separate payloads:

```vue [app.vue]
<script setup lang="ts">
import { useAsyncData } from '#imports'
import { navigation, useContentSearch } from '@lupinum/ginko-content/client'
import { docs } from '~/content.config'

const { locale } = useI18n()

const { data: layoutNavigation } = await useAsyncData(
  () => `docs-navigation:${locale.value}`,
  () => navigation(docs, { locale: locale.value }),
  { watch: [locale] }
)
const {
  query,
  files,
  searchNavigation
} = await useContentSearch({ collection: docs, locale })

provide('navigation', layoutNavigation)
</script>

<template>
  <NuxtLayout>
    <NuxtPage />
  </NuxtLayout>

  <ClientOnly>
    <LazyUContentSearch
      v-model:search-term="query"
      :files="files"
      :navigation="searchNavigation"
    />
  </ClientOnly>
</template>
```

`searchNavigation` (from `useContentSearch()`) is projected for search. Use `layoutNavigation` for sidebars and headers.

## Route pages

Use `useContentPage()` for localized dynamic content routes:

```vue [pages/docs/[...slug].vue]
<script setup lang="ts">
import { createError, useContentPage } from '#imports'
import { docs } from '~/content.config'

definePageMeta({
  content: {
    collection: 'docs',
    route: {
      en: '/docs',
      de: '/dokumentation'
    }
  }
})

const { page, previous, next } = await useContentPage(docs, {
  fallback: true,
  surround: { select: ['description'] }
})

if (import.meta.server && !page.value) {
  throw createError({ statusCode: 404, statusMessage: 'Page not found' })
}
</script>

<template>
  <main v-if="page">
    <ContentRenderer :value="page" />
    <UContentSurround :surround="[previous, next]" />
  </main>
</template>
```

`useContentPage()` resolves the active locale from the route, keeps the result stable through hydration, suppresses stale-route flashes, and returns `route`/`resolution` facts your page reads to publish locale params to Nuxt I18n — it does not raise a default 404, so check `page.value` yourself.
The `definePageMeta()` block is explicit validation metadata: Ginko checks it
against `content.config.ts` and reports mismatched or missing locale routes
during Nuxt page registration.

## List pages

Pair `many()` with `useAsyncData` for lists. It scopes the query to the current locale and each item carries a `route` (with `resolvedPath`):

```vue [pages/posts/index.vue]
<script setup lang="ts">
import { useAsyncData } from '#imports'
import { many } from '@lupinum/ginko-content/client'
import { posts } from '~/content.config'

const { locale } = useI18n()
const { data: postList } = await useAsyncData(
  () => `posts:${locale.value}`,
  () => many(posts, { locale: locale.value, sort: { date: 'desc' } }),
  { watch: [locale] }
)
</script>

<template>
  <ul>
    <li v-for="post in postList" :key="post.route.resolvedPath">
      <NuxtLink :to="post.route.resolvedPath">
        {{ post.title }}
      </NuxtLink>
    </li>
  </ul>
</template>
```

Do not build locale prefixes yourself. `post.route.resolvedPath` is already the UI route for the active locale.

## Locale switcher

Read `route.alternates` off a resolved page — no separate query or composable:

```vue [components/AppLocaleSelect.vue]
<script setup lang="ts">
import { docs } from '~/content.config'

const { locale } = useI18n()
const { page } = await useContentPage(docs, {
  fallback: true
})

const items = computed(() =>
  (page.value?.route.alternates ?? []).map(alternate => ({
    label: alternate.locale,
    to: alternate.locale === locale.value ? undefined : alternate.path
  }))
)
</script>
```

This uses the localized content path instead of guessing translated slugs in the component. Fall back to route-only Nuxt I18n switching only when the current route is not backed by a resolved content document.

## Validation

Run the i18n doctor after a build:

```bash
pnpm build
npx ginko-content doctor --i18n
```

Expected clean output:

```txt
Ginko Content doctor: ok
Root: /absolute/project/path

Info (1)
- .output/public/sitemap_index.xml: Sitemap mode: Nuxt Sitemap i18n multi-sitemap (2 child sitemaps, 20 URLs).
  Check: Submit "/sitemap_index.xml". Child sitemaps: __sitemap__/de-DE.xml (10 URLs), __sitemap__/en-US.xml (10 URLs).
```

The i18n doctor checks direct stale dependencies and APIs, collection `i18n: true`, locale folders, repeated prefixes such as `/de/de/`, child sitemaps, and generated search records.

## Artifact checks

Use these checks when validating the final production output:

```bash
test -f .output/public/sitemap.xml || test -f .output/public/sitemap_index.xml
find .output/public/__sitemap__ -name '*.xml' -maxdepth 1 -print 2>/dev/null || true
rg "/de/de/" .output/public
node -e "const data=require('./.output/public/api/_content/search/index.json'); const rows=Array.isArray(data)?data:data.records||[]; console.log(rows.reduce((a,r)=>({...a,[r.locale]:(a[r.locale]||0)+1}),{}))"
```

Nuxt Sitemap can emit a single root sitemap or a sitemap index with one child
sitemap per locale under `/__sitemap__/`. Submit the sitemap URL generated by
the configured mode.

If static generation leaves `.output/public/sitemap.xml/` as a redirect directory, do not add route rules or disable Nuxt Sitemap i18n mode only to force a physical `sitemap.xml` file. Validate the emitted root sitemap or index and child sitemaps instead.

Expected result:

```txt
.output/public/__sitemap__/en-US.xml
.output/public/__sitemap__/de-DE.xml
no /de/de/ matches
{ en: <number>, de: <number> }
```

Both locale counts must be greater than zero.
