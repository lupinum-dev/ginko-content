You do not need this page to use Ginko. It explains why the library is shaped the way it is, for contributors and the curious. This is the one page where the architecture vocabulary lives.

## Files are canonical

For the filesystem provider, files under `content/` and configured mounts are the source of truth. Parsed caches, normalized documents, locale indexes, navigation, search records, sitemap entries, and prerender routes are all derived. Discard any of them and Ginko rebuilds it from your files.

A derived surface is valid when four statements hold:

1. You can discard it without losing authored content.
2. Its inputs are documented.
3. Rebuilding from canonical state produces the expected result.
4. Tests protect the relationship between source and derivative.

The benefit: your application never reconciles a file with a second authoritative database record. Delete the search index and content survives; rebuild content and the index comes back.

## Collections are required

Every public content read targets a collection handle. There is no unscoped global content query.

Even a small project must declare its collections, and that cost buys something. Every document has a known schema, source, route policy, localization policy, and provider boundary. Types stay attached to reads, and validation and access policy have a place to live. An unscoped query would strip all of that.

## The lifecycle

Source input becomes a normalized document, then public features consume it. The direction never reverses.

1. **Discover** - the filesystem provider matches files against collection sources (Markdown, MDC, YAML, JSON, CSV). An external provider skips this and returns raw documents through the provider contract.
2. **Parse** - frontmatter and body become a renderable syntax tree or a data document. Parsing answers what the source contains, not its final route or locale.
3. **Transform** - Markdown plugins and transformers run: highlighting, table-of-contents extraction, project-specific AST work. Transformers must stay deterministic - same source and config, same document.
4. **Validate** - collection schemas check authored fields at ingestion. Strict mode rejects unknown or invalid frontmatter before it reaches a page. Validation belongs here because every later surface consumes the same accepted shape.
5. **Normalize** - Ginko adds the document envelope and route facts: collection ownership, canonical identity, locale, public path, resolution metadata, route variants. Providers return source facts; Ginko derives public route policy.
6. **Consume** - normalized documents feed `useContentPage` and `<ContentRenderer>`; `one`, `many`, and `paginate`; navigation and surroundings; MiniSearch, Pagefind, or provider-owned search; sitemap entries and prerender discovery; agent-readable Markdown.

No public surface reinterprets the original file on its own. When navigation and a page disagree about a route, the fix belongs in normalization, not in frontend glue.

## Who owns what

Ginko stays coherent by assigning each fact to one owner.

| Owner | Responsibilities |
| --- | --- |
| Ginko core | Normalized document contract, queries, route projection, rendering integration, variant resolution |
| Filesystem provider | File discovery, parsing input, ordering conventions, draft and partial conventions |
| External provider | Source truth, raw documents, route facts, supported query capabilities, source invalidation |
| Nuxt | Application routes, rendering lifecycle, Nitro deployment, prerender execution |
| Nuxt I18n | Active locale, URL strategy, static application-page localization |
| Nuxt Sitemap | XML, sitemap indexes, robots integration, final serialization |
| Application | Page layouts, 404 UX, component design, access policy, product-specific queries |
| CMS product | Editing, drafts, publishing, roles, assets, workflow, editorial audit |

The boundary is behavioral: providers return source facts, Ginko applies route policy, integrations project those facts into XML or their own formats, and applications decide presentation. If the application rebuilds content routes, it and Ginko can disagree. If Ginko owns XML, deployment concerns leak into the content engine.

## When a feature belongs in core

A proposed core feature answers three questions:

1. Does it serve the target content sites today?
2. Can it use an existing source of truth?
3. Can the behavior be proven across the public contract?

If the answer is no, the feature belongs in an application, a provider, or a separate product - not the core.
