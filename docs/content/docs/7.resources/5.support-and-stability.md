title: Support and Stability
description: Understand Ginko's supported runtime, public contract, pre-1.0 change policy, provider obligations, and issue-reporting expectations.
---

Ginko targets Nuxt 4 on Node.js 22.18–22.x, 24.11–24.x, or 26+. The package is ESM-only; CommonJS `require()` is not supported. Public package exports and documented behavior are compatibility commitments; internal files are not.

## Supported path

The maintained application path uses:

- current Nuxt 4;
- Node.js 22.18–22.x, 24.11–24.x, or 26+;
- collection handles from `content.config.ts`;
- the unified query API;
- `useContentPage` and `useContentSearch`;
- the filesystem provider or a conforming external provider;
- supported Nuxt I18n and Nuxt Sitemap versions when those integrations are enabled.

Exact supported ranges live in package metadata and are exercised by the minimum-runtime and dependency-canary CI lanes.

## Public contract

Supported import paths are listed in [Package exports](/docs/reference/package-exports). Imports from `src/`, generated virtual modules not documented for consumers, or internal runtime paths are unsupported.

The document envelope, query grammar, provider wire contract, and module options are public behavior. Changes to those surfaces require semver treatment, changelog notes, tests, and migration guidance.

## Pre-1.0 changes

Ginko may make hard cutovers before 1.0 when the foundation is wrong. Removed paths are not kept as indefinite aliases. Version-specific changes receive a migration guide.

Applications should pin intentional versions, review release notes, and test prereleases against production-shaped builds.

## Provider support

External providers own their source SDK, credentials, indexing, and operational behavior. A provider should run Ginko's official contract suite against every advertised capability and supported Ginko version.

## Security reports

Do not publish exploitable vulnerabilities in a public issue. Follow the repository's security policy and maintainer contact path.

## Useful issue reports

Include:

- a minimal reproduction;
- exact dependency and runtime versions;
- deployment target and provider;
- collection and module configuration;
- expected and actual behavior;
- complete logs;
- whether the problem reproduces in development, production build, or both.

## Release verification

Repository releases use the maintained verification and packed-consumer process. Agent sessions must not run live publish commands. Human maintainers inspect generated tarballs and follow `MAINTAINING.md`.
