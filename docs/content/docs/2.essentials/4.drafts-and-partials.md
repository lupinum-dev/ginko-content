Two conventions let you keep files in `content/` without routing them: drafts (hidden in production) and partials (never routed, always reusable).

## Drafts

A draft is a page that exists in `content/` but is hidden from production. It's visible in development so authors can preview it.

Three ways to mark a file as a draft:

**Frontmatter flag:**

```md [content/articles/future-work.md]
---
title: Future work
draft: true
---

# Future work
```

**Filename suffix:**

```txt
content/articles/future-work.draft.md
```

**Underscore convention for entire folders** — see partials below.

Query-time filtering happens automatically: in production, drafts are excluded from `many(docs)` results and from navigation. In development, they're included and rendered with a `draft` badge if your layout opts in.

You can inspect the flag manually:

```ts
const { page } = await useContentPage(articles)

if (page.value?.draft) {
  // Render a "Draft" indicator
}
```

### Previewing drafts outside development

`one()` and `many()` do not accept a `where` clause that overrides visibility — `one()` only takes `by`, `select`, `locale`, `fallback`, and `populate`, and draft/partial hiding is enforced by the filesystem provider's query policy before your options are applied, not by a filter you can out-argue with `where: { draft: true }`.

In `nuxt dev`, drafts and partials are always visible, so the query above already works with no special option:

```ts
import { one } from '@lupinum/ginko-content/client'

const draft = await one(articles, {
  by: { path: route.path }
})
```

Outside development, this is filesystem preview: configure `content.preview.token` in `nuxt.config.ts`, then send that token as `previewToken` in the query string, an `x-nuxt-content-preview` header, or a `previewToken` cookie. Requests carrying the matching token see drafts and partials too, using the same `one()`/`many()` calls above — no different options or endpoints.

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  content: {
    preview: {
      token: process.env.GINKO_CONTENT_PREVIEW_TOKEN
    }
  }
})
```

This only reveals drafts/partials that are already present in the deployed content directory — the filesystem provider cannot fetch content that has not been committed and deployed. Treat it as a development/staging convenience, not a production preview workflow. A real "preview content that has not been published yet" workflow (draft fetched from a CMS before publish) is the responsibility of a CMS provider that implements its own preview-aware `page()`/query methods; the filesystem provider does not provide one.

## Partials

A partial is a file that's parsed and queryable but never routed. Two conventions trigger it:

**Underscore-prefixed filename:**

```txt
content/docs/
  _shared-intro.md      → partial
  getting-started.md    → /docs/getting-started
```

**Underscore-prefixed folder** — everything inside becomes a partial:

```txt
content/
  _snippets/
    install.md          → partial
    config.md           → partial
```

Use cases:

- Shared boilerplate (install instructions, legal footer) included in multiple pages
- MDC components stored as Markdown fragments
- Data-only documents consumed by page components

### Using a partial

Partials are queryable like any other document:

```ts
const intro = await one(docs, {
  by: { path: '/docs/_shared-intro' }
})
```

Render it with `<ContentRenderer>` inside any page:

```vue
<template>
  <ContentRenderer v-if="intro" :value="intro" />
</template>
```

### Partial metadata

Partials can still carry frontmatter. Use it to parameterise the fragment:

```md [content/_snippets/install.md]
---
command: npx nuxi module add @lupinum/ginko-content
---

Run the following in your project:

`{{ $doc.command }}`
```
