title: References
description: Link documents across collections with typed, validated references.

A reference is a pointer from one document to another. Prefer `fields.relation()` for one reference and `fields.relations()` for many references. These helpers keep the Zod validation, and they also give CMS integrations enough metadata to render relation pickers.

## A minimal reference

An article references one author:

```ts [content.config.ts]
import { defineCollection, defineContentConfig, fields } from '@lupinum/ginko-content/config'
import { z } from 'zod'

export const authors = defineCollection({
  type: 'data',
  source: 'authors/**/*.md',
  schema: z.object({
    name: fields.text().required(),
    avatar: fields.object({
      src: fields.image().required(),
      alt: fields.text()
    })
  })
})

export const articles = defineCollection({
  type: 'page',
  source: 'articles/**/*.md',
  schema: z.object({
    title: fields.text().required(),
    author: fields.relation('authors').required()
  })
})

export default defineContentConfig({
  collections: { authors, articles }
})
```

In the Markdown file, the reference is a string:

```md [content/articles/hello.md]
---
title: Hello, world
author: jane-doe
---

# Hello, world
```

At query time the field stays a string:

```ts
import { one } from '@lupinum/ginko-content/client'

const article = await one(articles, {
  by: { path: '/articles/hello' }
})

article.author // "jane-doe"
```

That is intentional. Ginko validates and types the field, but does not silently inline another document into the query result.

## Many-to-many

Tag articles with multiple topics:

```ts
defineCollection({
  type: 'page',
  source: 'articles/**/*.md',
  schema: z.object({
    title: fields.text().required(),
    topics: fields.relations('topics')
  })
})
```

```md [content/articles/hello.md]
---
title: Hello, world
topics: [intro, markdown]
---
```

The stored value is still an array of strings.

## Matching rules

A reference matches in this order:

1. The target's canonical key
2. `ref` frontmatter of a target document
3. The target's path and source-path candidates

Use `ref` when you want a stable alias that survives file renames. (Frontmatter
`id` is reserved by the system and no longer acts as a reference alias — use
`ref` instead.)

```md [content/authors/jane-doe.md]
---
ref: author-jane
name: Jane Doe
---
```

`author-jane` matches from another document.

Markdown body links can use the same identity vocabulary with a `$` prefix:

```md
Read the [intro]($docs.intro#setup).
```

Ginko resolves `$docs.intro` through the content graph when the source document
is queried. In localized collections, the rendered link points at the requested
locale's variant and falls back through the configured locale chain when a
translation is missing. Fallback links keep the requested-locale URL and serve
the fallback document.

## Querying references

Reference fields are plain strings at the storage layer. Query them like any other field:

```ts
import { many } from '@lupinum/ginko-content/client'

const byJane = await many(articles, {
  where: { author: 'jane-doe' }
})

const tagged = await many(articles, {
  where: { topics: { $contains: 'intro' } }
})
```

## Backlinks

Use `backlinks()` when you have a target document and need the source documents that reference it. Typed source handles infer top-level `reference()` fields automatically. `backlinks()` comes from `@lupinum/ginko-content/client` — it is not auto-imported, so pair it with `useAsyncData` in components.

```ts
import { backlinks } from '@lupinum/ginko-content/client'

const postsByJane = await backlinks(authors, {
  by: { ref: 'jane-doe' },
  from: articles,
  sort: { date: 'desc' }
})
```

In Vue components, pair it with `useAsyncData` and a stable, reactive key:

```ts
import { useAsyncData } from '#imports'
import { backlinks } from '@lupinum/ginko-content/client'

const route = useRoute()
const { data: articles } = await useAsyncData(
  () => `backlinks:${route.params.author}`,
  () => backlinks(authors, { by: { ref: String(route.params.author) }, from: articles }),
  { watch: [() => route.params.author] }
)
```

## Resolving a reference target

When you need the referenced document itself, resolve it explicitly on the server:

```ts [server/api/author.get.ts]
import { one } from '#content/server'
import { articles, authors } from '~/content.config'

export default defineEventHandler(async (event) => {
  const article = await one(event, articles, {
    by: { path: '/articles/hello' }
  })

  if (!article?.author) {
    return null
  }

  return one(event, authors, {
    by: { ref: article.author }
  })
})
```

Reference resolution respects locale fallback when you pass `locale` and `fallback` options.

## Populating references

Manual resolution works, but when a page or list needs the referenced document inline, use `populate` instead of a second round trip. `populate` is a `{ field: targetCollection }` map passed alongside `where`/`select`/etc. Ginko resolves each named field's stored ref string into the target document and replaces the field in the result:

```ts
import { one } from '@lupinum/ginko-content/client'
import { articles, authors } from '~/content.config'

const article = await one(articles, {
  by: { path: '/articles/hello' },
  populate: { author: authors }
})

article.author // the full author document, or null if unresolved
```

`populate` works the same way on `many()`, `paginate()`, `resolveOne()`, and `backlinks()`:

```ts
import { many } from '@lupinum/ginko-content/client'
import { articles, authors } from '~/content.config'

const list = await many(articles, {
  populate: { author: authors }
})

list[0].author?.name
```

Array `reference()`/`relations()` fields populate to an array of resolved documents in the same order, with unresolved entries filtered out:

```ts
defineCollection({
  type: 'page',
  source: 'articles/**/*.md',
  schema: z.object({
    title: fields.text().required(),
    topics: fields.relations('topics')
  })
})
```

```ts
import { one } from '@lupinum/ginko-content/client'

const article = await one(articles, {
  by: { path: '/articles/hello' },
  populate: { topics }
})

article.topics // Array<Topic>
```

Rules:

- When the schema declares a field as `reference()`/`relation()`/`relations()`, `populate` must point that field at one of the collections the schema allows. Pointing it at a different collection throws at query time so drift is caught immediately instead of silently returning the wrong document.
- Populated documents go through the same locale resolution as the outer query — pass `locale`/`fallback` on the outer options and they apply to the populated lookups too.
- `select` does not need to repeat populated field names; Ginko keeps them in the projected result automatically so `populate` can fill them in.
- Populating does not recurse — the populated document is not itself populated. Resolve nested references with a second explicit `one()`/`many()` call.
