---
title: Ginko and Nuxt Content
description: Choose Ginko for a focused filesystem and localization model; choose Nuxt Content for its SQL storage and Studio ecosystem.
---

Ginko and Nuxt Content share familiar Nuxt concepts, but optimize for different projects. This comparison is a selection guide, not a claim that one library should replace the other everywhere.

The comparison below was reviewed against the official Nuxt Content v3 documentation in July 2026.

## Shared ground

Both libraries provide:

- collections declared in `content.config.ts`;
- typed schemas and collection queries;
- Markdown and MDC rendering;
- page and data collections;
- navigation and content-search building blocks;
- integration with Nuxt applications and deployment targets.

The decision is about architecture and product scope.

## Decision table

| Decision | Ginko | Nuxt Content |
| --- | --- | --- |
| Product center | Small-to-medium filesystem-first sites | A broader Git-based content platform |
| Canonical filesystem state | Files remain canonical; runtime artifacts are derived | Files are parsed into SQL-backed storage |
| Runtime storage | No content database in the default provider | SQLite-backed storage with runtime adapters |
| Query model | Collection handles with unified page, list, navigation, and server verbs | Collection query builder backed by SQL |
| Localization | Locale variants, fallback, canonical identity, and translated slugs are core concepts | Official integration uses locale-specific collections and application resolution |
| Browser editing | Outside Ginko core | Nuxt Studio provides a self-hosted editing workflow |
| Search | MiniSearch, Pagefind, or provider-owned search | Collection search sections and the wider Nuxt Content ecosystem |
| External sources | Providers return normalized documents and route facts | Database adapters configure the storage backend |
| Best fit | Coherent content sites that value fewer moving parts | Projects that value SQL-backed querying or Studio integration |

## Choose Ginko when

- files and Git are the preferred authoring workflow;
- multilingual content needs fallback and translated routes without application-owned mapping tables;
- installation must avoid a runtime content database;
- navigation, search, sitemap, and prerender should derive from one route model;
- the application should keep the same API when an external provider is introduced later;
- the project accepts a focused small-to-medium site target.

## Choose Nuxt Content when

- SQL-backed content storage is a positive requirement;
- the project needs Nuxt Studio's browser editing workflow;
- large collection querying matters more than filesystem simplicity;
- the team prefers Nuxt Content's larger ecosystem and upstream direction;
- the official locale-per-collection integration matches the application's needs.

## Important Nuxt Content details

Nuxt Content v3 generates a database dump and restores it into SQLite. Client-side queries can use a browser WASM SQLite database. Its current Node installation can use `better-sqlite3`, `sqlite3`, or native SQLite on supported Node versions. Ginko should therefore not be selected on the outdated claim that Nuxt Content always requires one specific native package.

Nuxt Studio is a free, open-source, self-hosted module. Teams that need browser editing today should treat that as a concrete Nuxt Content advantage, not an incidental add-on.

The official Nuxt Content i18n guide defines a collection per locale and resolves fallback in application code. Ginko makes that concern part of the content model instead.
