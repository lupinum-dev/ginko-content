---
title: When Not to Use Ginko
description: Do not choose Ginko when browser editing, database-scale content, or runtime editorial workflows are primary requirements.
---

Ginko is intentionally not the right content system for every Nuxt application.

Choose another platform when the missing capability is central to the project, not a distant possibility.

## Browser-first editing is required

Ginko core does not include a Studio, admin panel, uploads, roles, or collaborative editing. Git-backed tools can sit above the files, and external providers can connect another source, but neither is a built-in editorial product.

Choose Nuxt Content with Nuxt Studio or a dedicated CMS when non-technical authors must edit and publish in a browser today.

## Content must publish without deployment

The filesystem provider reads deployed files. It cannot reveal a file that was never committed or deployed.

Use a CMS-backed provider or another runtime content platform when editors must publish independently from application releases.

## The dataset is very large

Ginko's default model targets a few hundred documents and should remain reasonable around 2,000 Markdown documents, depending on content size, locales, search, and deployment.

Use a dedicated provider, external search service, or database-oriented platform when large datasets and ad hoc queries define the project.

## Editorial workflow is the product

Permissions, approval states, scheduled publishing, asset governance, audit policy, and live collaboration are CMS concerns. Ginko's provider contract can consume published content from such a system, but Ginko core does not implement the workflow.

## SQL-backed client querying is desired

Ginko offers typed content queries, but the default provider is not a browser SQL database. Choose Nuxt Content when local SQL-backed querying and its database architecture are advantages for the application.

## Nuxt 4 is not the application framework

Ginko's module and application integrations target Nuxt 4. Pure data-source and portability exports serve advanced integrations, but Ginko is not a framework-neutral site generator.

## If only one requirement is missing

Do not add infrastructure preemptively. A site that fits Ginko today should not adopt a CMS because it might need one later. The provider boundary exists so a real source can replace the filesystem provider without rewriting the application-facing content model.
