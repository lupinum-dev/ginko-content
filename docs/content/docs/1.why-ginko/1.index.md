---
title: Why Ginko
description: Ginko keeps content-heavy Nuxt sites coherent by making collections the boundary and treating files as canonical input.
---

Ginko is for Nuxt teams that want content to stay close to the application without turning the application into a content platform.

Write Markdown, YAML, JSON, or CSV in `content/`. Define collections once. Ginko then uses those collections for route resolution, typed queries, navigation, localization, search, sitemap entries, and server reads.

## The product decision

Most content systems optimize for the largest project they might eventually serve. The common path then inherits databases, adapters, synchronization, and editorial infrastructure before it needs them.

Ginko makes a narrower choice:

- optimize the filesystem workflow for small-to-medium content sites;
- keep one public query model across pages and providers;
- treat localization as part of document identity;
- derive navigation, search, sitemap, and prerender output from content;
- keep CMS workflow and browser editing outside the core.

That choice is useful only when it matches the project. Start with [Who Ginko is for](/docs/why-ginko/who-it-is-for), then read [When not to use Ginko](/docs/why-ginko/when-not-to-use-ginko).

## The smallest complete model

Define a collection:

```ts [content.config.ts]
import { defineCollection, defineContentConfig } from '@lupinum/ginko-content/config'

export const docs = defineCollection({
  type: 'page',
  source: 'docs/**/*.md',
  route: '/docs'
})

export default defineContentConfig({
  collections: { docs }
})
```

Resolve the current route through that collection:

```vue [pages/docs/[...slug].vue]
<script setup lang="ts">
import { docs } from '~/content.config'

const { page } = await useContentPage(docs)
</script>

<template>
  <ContentRenderer v-if="page" :value="page" />
</template>
```

The collection is not configuration around a global content bag. It is the owner of these documents. Its schema, route mount, localization policy, and provider behavior flow into every read.

## What this buys

- **One source of truth:** files are canonical for the filesystem provider.
- **One query vocabulary:** page, list, navigation, and server reads use collection handles.
- **One route model:** public paths, locale variants, and sitemap entries use the same route facts.
- **One deployment story:** the default path does not initialize a runtime content database.
- **One extension boundary:** external systems implement the provider contract without changing application pages.
