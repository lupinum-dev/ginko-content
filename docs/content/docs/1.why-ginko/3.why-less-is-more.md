---
title: Why Less Is More
description: Ginko limits the default system to one source of truth, one query model, and explicit ownership so content sites remain understandable.
---

Ginko removes capabilities from the core when their ongoing complexity costs more than they help the target project.

This is not minimalism for its own sake. Each limitation protects an invariant that users can rely on.

## Files are canonical

For the filesystem provider, files under `content/` and configured mounts are the source of truth.

Parsed caches, normalized documents, locale indexes, navigation, search records, sitemap entries, and prerender routes are derived. They can be discarded and rebuilt from the files.

**Limitation:** filesystem content changes through the repository and deployment workflow.

**Benefit:** the application never has to reconcile a file with a second authoritative database record.

## Collections are required

Every public content read targets a collection handle. Ginko does not expose an unscoped global content query.

**Limitation:** even a small project must declare its collections.

**Benefit:** every document has a known schema, source, route policy, localization policy, and provider boundary. Types remain attached to reads.

## No runtime content database by default

The filesystem provider does not require a SQL store or native database binding. Content is prepared from files and served through portable runtime artifacts.

**Limitation:** the default provider is not designed for database-scale ad hoc queries.

**Benefit:** installation, CI, containers, serverless builds, and local agents do not need content-database setup.

## Localization is not application glue

Locale variants share a canonical document identity. Fallback, language switching, navigation merging, and translated slugs resolve through that identity.

**Limitation:** localized collections follow explicit conventions and validation.

**Benefit:** page components do not maintain their own locale collection maps, fallback chains, or slug reconciliation.

## CMS workflow stays outside core

Ginko core does not ship a Studio, roles, uploads, editorial state, or runtime mutation API.

**Limitation:** teams that need those features must use another product or an external provider.

**Benefit:** filesystem users do not carry CMS concepts through parsing, querying, rendering, and deployment.

## Providers preserve the application contract

An external source can implement the provider contract and serve the same normalized documents and route facts.

**Limitation:** provider authors must implement and test a real contract.

**Benefit:** application pages do not branch on filesystem, CMS, or database source names.

## The admission rule

A new core feature should answer three questions:

1. Does it serve the target content sites today?
2. Can it use an existing source of truth?
3. Can the behavior be proven across the public contract?

If the answer is no, the feature probably belongs in an application, provider, or separate product.
