---
title: Choosing a search backend
description: Decide when to use MiniSearch, Pagefind, or an external search service.
---

Choose the backend based on what has to happen at query time. MiniSearch and Pagefind are built in and work for generated sites. Provider-owned search delegates to the active content provider. External search services are for cases where search needs product-level behavior beyond a static content index.

## Start with the UI surface

The search UI and the search backend are separate choices.

| Need | Use |
|---|---|
| Nuxt UI command palette | `useContentSearch({ collection })` with `UContentSearch` |
| Headless combobox or keyboard palette state | `useContentSearch()` |
| Custom input, modal, or results page | `useContentSearch()`, driven by `setQuery()` |
| Built-in static backend | MiniSearch or Pagefind |
| Provider-owned content search | `engine: 'provider'` |
| Hosted or self-hosted search platform | Algolia, Meilisearch, Typesense, OpenSearch, or a similar service |

`UContentSearch` is a UI component. MiniSearch, Pagefind, and external services are search backends.

## Use MiniSearch for the default static index

The MiniSearch backend is the default. It is the shortest path when your content set can be searched from one generated index.

Use MiniSearch when:

- you want the least configuration
- your content is mostly static
- one generated index is acceptable for your users
- you do not need custom ranking, facets, analytics, or per-user visibility

MiniSearch is also a good first implementation while you are still validating the search experience.

## Use Pagefind for larger static sites

Pagefind keeps the static hosting model, but changes how the browser loads the search index.

Use Pagefind when:

- you want search to work from static files
- your docs or article archive has grown beyond the shape you want for one MiniSearch index
- you want the browser to load matching search assets instead of one full index
- you do not want to run or operate a search server

The app code can keep using `useContentSearch()` after switching to Pagefind.

## Use provider-owned search for provider-backed sites

Use provider-owned search when the active content provider owns indexing and ranking, such as a database-backed content source or future CMS provider.

Use provider-owned search when:

- content changes without a static rebuild
- search should use provider-side permissions or visibility rules
- you do not want the Nuxt app to build a local search index
- the provider already has better text search than the filesystem runtime

## Use an external service for product search behavior

Use an external engine when search is more than static content lookup.

Consider Algolia, Meilisearch, Typesense, OpenSearch, or a similar service when you need:

- custom ranking, synonyms, typo tolerance, or advanced relevance controls
- facets, filters, sorting, or analytics
- private, permissioned, or per-user results
- real-time updates without regenerating the site
- one search experience across docs, product data, support articles, or app records
- very large indexes that should not be shipped as static site assets

Ginko does not wrap those services. Build the indexing pipeline and UI against the provider you choose.

## Decision table

| Requirement | Pick |
|---|---|
| Shortest built-in setup | MiniSearch |
| Static hosting with a sharded search index | Pagefind |
| Provider-backed content with provider-owned search | Provider-owned search |
| Nuxt UI command palette | `useContentSearch({ collection })` with `UContentSearch` |
| Headless combobox or command palette state | `useContentSearch()` |
| Custom search UI over built-in search | `useContentSearch()`, driven by `setQuery()` |
| Custom ranking, facets, synonyms, or analytics | External search |
| Private or per-user results | External search |
| Search across content and app data | Provider-owned or external search |

There is no fixed page-count threshold for switching backends. Check the generated index size, loading behavior, and the kind of search controls your users need.
