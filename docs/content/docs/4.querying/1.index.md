The unified query API reads through collection handles from `content.config.ts`. Use the async functions (`one`, `many`, `resolveOne`, `variants`, `tree`, `neighbors`) in plain async code, and the `useContent*` composables when you want Nuxt async-data state.

## The shape

```ts
import { many } from '@lupinum/ginko-content/client'
import { articles } from '~/content.config'

const latest = await many(articles, {
  where: { published: true },
  sort: { date: 'desc' },
  limit: 5
})
```

The options stay explicit:

- `where` for filters
- `$and`, `$or`, and `$not` for grouped logic
- `sort` for ordering
- `select` for projection
- `limit` and `skip` for paging
- `by` for route, path, or ref lookup
- `populate` for inlining `reference()` fields into the result

Use `by: { path }` when you need an exact content path:

```ts
import { one } from '@lupinum/ginko-content/client'

const page = await one(articles, {
  by: { path: '/articles/launch-notes' }
})
```

## Route-backed pages

For content-backed routes, use the page helper:

```ts
import { docs } from '~/content.config'

const { page } = await useContentPage(docs)
```

That keeps route-keyed loading, stale-result masking, locale variants, and content-route registration on the package side instead of rebuilding them in app code.

## Result helpers

| Method | Result |
|---|---|
| `many(articles, options)` | `T[]` |
| `one(articles, options)` | `T \| null` |
| `resolveOne(articles, options)` | `{ doc, explain }` |
| `tree(docs, options)` | navigation tree |
| `neighbors(docs, options)` | previous/next entries |

Raw string collection names remain supported for dynamic/plugin code, but app code should prefer collection handles because they preserve schema inference.
